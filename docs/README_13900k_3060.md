# Run r4 on the i9-13900K / 32 GB / RTX 3060 12 GB PC

This is the recommended desktop profile for the accuracy update on `r4`.
**It has only had static review. Training, inference, regression tests, the GPU
probe, and the Windows launcher have not been executed on the author's Mac.**
Runtime, peak RAM/VRAM, and accuracy must be measured on the PC.

## Start on Windows

Install 64-bit Python 3.12 and an up-to-date NVIDIA driver. Clone onto an SSD.
Allow roughly **100 GB of free SSD space** for intermediate files and temporary
country partitions. This is a planning allowance, not a measured requirement.

```powershell
git clone --branch r4 https://github.com/Aditya-1209/Star_Coders_Amazon_ML_Challenge.git
cd Star_Coders_Amazon_ML_Challenge
```

For an existing clone, use `git fetch origin`, `git switch r4`, then
`git pull --ff-only origin r4`.

Copy the organizer ZIP into this folder and extract it if necessary:

```powershell
py -3.12 -m zipfile -e amazon_ml_dataset.zip .
```

Then run:

```powershell
.\scripts\run_r4_pc.cmd
```

The launcher creates `.venv-r4`, installs the pinned v2 dependencies, checks CUDA
with a tiny one-tree synthetic fit, runs the synthetic regression suite, then
prepares/trains/predicts/validates the full workflow. It stops on any failed
command. It does not submit or publish anything. CUDA fallback to CPU is rejected
by the preflight so a broken GPU setup is caught before the long run.

The same Python runner works on Linux after installing `requirements_v2.txt` in
a Python 3.12 virtual environment:

```bash
python scripts/run_r4_desktop.py
```

## What is tuned for this machine

Settings are in [`configs/desktop_13900k_3060.json`](../configs/desktop_13900k_3060.json).

| Component | Profile setting | Purpose |
| --- | --- | --- |
| Text normalization | 8 processes; 250,000-row input windows | Bound queued Python strings and process payloads |
| Polars and fuzzy features | 12 threads | Avoid launching 32 workers and multiplying memory use |
| Blocking joins | 5,000 businesses per chunk | Reduce join intermediates versus the old 100,000 |
| Blocking/features/graph | One country at a time | Reduce simultaneous normalized tables and key indexes |
| Feature files | 500,000 pairs per shard | Bound record attachment and similarity arrays |
| XGBoost training | CUDA; 12 host threads | Use the RTX 3060 for tree training |
| Training matrix construction | 100,000 rows per dense batch | Avoid a full extra float32 copy of the training fold |
| Histogram cache | 4,096 nodes; 256 bins retained | Limit histogram cache growth without reducing tree depth or bins |
| Prediction | CPU; 16 threads; 100,000 rows per batch | Match the existing CPU/NumPy inputs without CUDA device-mismatch conversion |
| Graph support | 1,000 businesses per chunk | Bound candidate-to-anchor comparisons |

GPU training and CPU prediction are separate settings. CPU prediction is an
engineering choice for the current host-memory features, not a measured claim
that it is faster than GPU prediction. The actual throughput is recorded in the
run logs. XGBoost documents its [iterator interface](https://xgboost.readthedocs.io/en/stable/python/python_api.html#xgboost.DataIter),
[histogram cache setting](https://xgboost.readthedocs.io/en/stable/parameter.html#parameters-for-non-exact-tree-methods),
and [CPU/GPU interoperability](https://xgboost.readthedocs.io/en/stable/gpu/).

The implementation also eliminates repeated full-context joins during shard
scoring and redundant stage-1 predictions on the rankers' own training groups.
Graph support slices sorted candidate rows instead of scanning the whole graph
for every support batch. Completed country intermediates are written to the SSD
and released before the next country.

The profile keeps the accuracy configuration: combined/name/address retrieval
limits of 64/16/8, all 63 pair features, both rankers trained on folds 0/8 and 1/9,
tree depth 10, and validation-selected graph blending. Global record indices and
the global target count used in IDF are preserved across country partitions.
Batching and country ordering can change quantiles and random subsampling, so
trained weights and scores may differ. This is not a promise of identical
trained weights or a higher score.

These are memory reductions, **not a hard 32 GB RAM or 12 GB VRAM limit**.
Country tables, global competition features, training frames, and quantized
matrices still reside in memory. The first run must establish whether further
reductions are necessary for this dataset and installed library versions.

## Progress and restarting

Default locations:

- Workspace, models and run record: `work/desktop_13900k_3060/`
- Per-step logs: `work/desktop_13900k_3060/logs/`
- Final outputs: `output/desktop_13900k_3060/`
- Stage-2 comparison outputs: `output/desktop_13900k_3060-stage2/`

Training data is processed first. Test preprocessing starts after training,
and every stage gets a separate process so memory is released between stages.
Run only one launcher against a workspace at a time.

Resume after a completed stage or a failed command:

```powershell
.\scripts\run_r4_pc.cmd --resume
```

The launcher skips only recorded successful stages after checking their output
file sizes/timestamps and commands. It reruns the CUDA preflight. A changed code
version or dataset requires a fresh workspace; mere file existence never counts
as success. This is **stage-level resume**, not resumption inside an interrupted
training job, normalization file, feature shard, or graph construction.

An interrupted feature stage deliberately leaves `_INCOMPLETE` and refuses to
mix partial shards with a new attempt. Preserve or remove **only the failed
feature folder** before resuming. For example, to preserve a failed training
feature folder:

```powershell
Rename-Item work\desktop_13900k_3060\feats_train feats_train.failed
.\scripts\run_r4_pc.cmd --resume
```

The preserved folder consumes disk space; use an unused backup name if repeating
this operation. Completed feature folders should not be removed.

To run only through training:

```powershell
.\scripts\run_r4_pc.cmd --to-step stage3_train
```

To print the plan without installing dependencies, importing ML libraries, or
starting any work:

```powershell
py -3.12 scripts\run_r4_desktop.py --plan
```

## If the PC runs out of memory

Copy the profile JSON to another file and reduce the setting for the failed
stage. The launcher accepts `--profile path\to\profile.json`. Start with
`block_chunk: 1000`, `feature_shard_pairs: 250000`, `matrix_batch_rows: 50000`,
`predict_batch_rows: 50000`, or `support_anchors: 250`, as relevant. Lowering the
dense batch size does not shrink the full training frame or quantized matrix.
For GPU histogram pressure, try `hist_cache_nodes: 1024`; close other GPU jobs.

Restart at the earliest stage affected by the changed profile:

```powershell
.\scripts\run_r4_pc.cmd --profile configs\my_smaller_profile.json --from-step train
```

Previously completed upstream commands/outputs must still match. Dependent
stages are invalidated and rerun, preventing stale predictions after retraining.
For example, restarting training retains unchanged test preprocessing while
rerunning graph training and predictions. A feature stage that needs rebuilding
still requires its existing output folder to be cleared or renamed, whether
that folder came from a failed attempt or an earlier completed generation.
If even the training frame does not fit, the manual `er_v2.train`
`--no-extra-stage1-folds` option in the general guide trades training data for
memory; the supplied desktop profile does not enable that accuracy tradeoff.

## Results

The run record marks the workflow complete only after the official validator
returns success. Inspect its log for warnings too. Read `models/metrics.json`
and `models/stage3_metrics.json` inside the workspace: `fold4_selected` reports
the selected model's holdout score. The old 0.9494 score is not this run's result.
The full modeling protocol and submission packaging steps are in the
[r4 accuracy guide](README_r4.md).
